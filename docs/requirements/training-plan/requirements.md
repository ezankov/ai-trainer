# Requirements Document

## Introduction

This feature introduces Training Plans into the AI Trainer application. A Training Plan is a structured multi-week running programme generated by an AI model, composed of daily Workouts arranged into weekly blocks. Athletes can create multiple plans targeting different race distances and events, but only one plan may be active at any time. The feature includes a plan creation flow where the athlete specifies duration, target distance, race event details, target pace, and the AI model to use for generation. The UI presents plans in two views: an active plan view showing week-by-week workout cards (inspired by the Runna app layout), and a plan management list for viewing, activating, and deleting non-active plans.

## Glossary

- **Training_Plan**: The JPA entity representing a structured multi-week running programme. Stored in the `trainer.training_plans` table. Contains metadata (name, duration, distance, race date, event name, target pace, AI model, state) and an ordered collection of planned Workouts grouped by week. Belongs to a User.
- **Plan_State**: An enumeration of training plan lifecycle states: NEW (created but generation not yet complete), ACTIVE (currently being followed by the athlete), COMPLETED (all weeks finished), TERMINATED (manually ended before completion).
- **Plan_Duration**: An enumeration of supported plan durations: WEEKS_8, WEEKS_10, WEEKS_12.
- **Plan_Distance**: An enumeration of supported target race distances: FIVE_K, TEN_K, HALF_MARATHON, MARATHON.
- **AI_Model**: An enumeration of supported AI models for plan generation: CHATGPT, CLAUDE, GEMINI, KIRO, DUMMY. DUMMY generates a placeholder training plan for UI validation purposes without calling a real AI service.
- **Target_Pace**: The athlete's goal race pace stored internally as an integer in seconds per kilometre (e.g., 300 represents 5:00/km). Target_Pace is always displayed to users in MM:SS/km format (minutes:seconds per kilometre) in all UI views, and communicated to AI models in MM:SS/km format during plan generation.
- **Training_Plan_API**: The Spring Boot REST controller handling endpoints under `/api/training-plans` for CRUD and state management operations on Training Plan resources.
- **Training_Plan_Service**: The backend service layer responsible for business logic related to creating, reading, updating state, and deleting Training Plans.
- **Plan_Workout**: The join entity linking a Training Plan to a Workout with additional scheduling metadata (week number, day of week, order within day). Stored in the `trainer.plan_workouts` table.
- **Plans_Page**: The Angular standalone component that displays the training plans feature with two tabs: the active plan view and the plan management list.
- **Active_Plan_View**: The tab within Plans_Page that displays the currently active Training Plan as weekly cards with expandable workout details.
- **Plan_List_View**: The tab within Plans_Page that lists all non-active Training Plans with management actions (delete, activate).
- **Week_Card**: A UI card component displaying a summary of all workouts scheduled for a given week within the active plan.
- **Training_Days**: An array of day-of-week values (integers 1=Monday through 7=Sunday) representing which days of the week the athlete wants to train. Must contain at least 1 and at most 7 values, with no duplicates. Stored as part of the Training_Plan entity.
- **Long_Run_Day**: A single day-of-week value (integer 1=Monday through 7=Sunday) representing which day the athlete prefers for their long run. Must be one of the selected Training_Days values.
- **User**: A person with a record in the `trainer.users` table who owns zero or more Training Plans.
- **Workout**: An existing entity representing a structured training session (see workouts feature). Training Plans reference Workouts via the Plan_Workout join entity.

## Requirements

### Requirement 1: Create Training Plan

**User Story:** As a logged-in athlete, I want to create a new training plan by specifying my race details and preferences, so that an AI model can generate a personalised multi-week running programme for me.

#### Acceptance Criteria

1. WHEN a POST request is sent to `/api/training-plans` with a valid payload containing `eventName`, `distance`, `duration`, `raceDate`, `targetPaceSecondsPerKm`, `aiModel`, `trainingDays`, and `longRunDay`, THE Training_Plan_API SHALL create a new Training_Plan record associated with the authenticated User with state set to NEW and return HTTP 201 with the created plan including its generated identifier and the metadata fields: `id`, `eventName`, `distance`, `duration`, `raceDate`, `targetPaceSecondsPerKm`, `aiModel`, `trainingDays`, `longRunDay`, `state`, `createdAt`, and `updatedAt`.
2. WHEN a POST request is sent to `/api/training-plans` with any required field (`eventName`, `distance`, `duration`, `raceDate`, `targetPaceSecondsPerKm`, `aiModel`, `trainingDays`, or `longRunDay`) missing or null, THE Training_Plan_API SHALL return HTTP 400 with a validation error message identifying each missing field.
3. WHEN a POST request is sent to `/api/training-plans` with an `eventName` that is blank (empty or whitespace-only) or longer than 100 characters, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the name must be between 1 and 100 non-whitespace characters.
4. WHEN a POST request is sent to `/api/training-plans` with a `distance` value that does not match any defined Plan_Distance enumeration value, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the invalid distance.
5. WHEN a POST request is sent to `/api/training-plans` with a `duration` value that does not match any defined Plan_Duration enumeration value, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the invalid duration.
6. WHEN a POST request is sent to `/api/training-plans` with a `raceDate` that is in the past relative to the current server date, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the race date must be in the future.
7. WHEN a POST request is sent to `/api/training-plans` with a `raceDate` that is not a valid ISO 8601 date (YYYY-MM-DD), THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the date format is invalid.
8. WHEN a POST request is sent to `/api/training-plans` with a `targetPaceSecondsPerKm` value less than 150 or greater than 900, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the pace is outside the valid range (2:30/km to 15:00/km).
9. WHEN a POST request is sent to `/api/training-plans` with an `aiModel` value that does not match any defined AI_Model enumeration value (CHATGPT, CLAUDE, GEMINI, KIRO, DUMMY), THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the invalid AI model.
10. WHEN a POST request is sent to `/api/training-plans` with a `trainingDays` array that is empty, contains more than 7 values, contains values outside the range 1–7, or contains duplicate values, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the training days are invalid.
11. WHEN a POST request is sent to `/api/training-plans` with a `longRunDay` value that is less than 1 or greater than 7, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the long run day is outside the valid range.
12. WHEN a POST request is sent to `/api/training-plans` with a `longRunDay` value that is not included in the provided `trainingDays` array, THE Training_Plan_API SHALL return HTTP 400 with a validation error message indicating the long run day must be one of the selected training days.
13. IF a POST request is sent to `/api/training-plans` without a valid JWT token or with an expired token, THEN THE Training_Plan_API SHALL return HTTP 401 with an error message indicating authentication is required.
14. THE Training_Plan_Service SHALL automatically populate `createdAt` on entity creation and `updatedAt` on every entity modification using the server's current UTC timestamp.

### Requirement 2: Single Active Plan Constraint

**User Story:** As a logged-in athlete, I want only one training plan to be active at a time, so that I have a clear focus on my current training programme without conflicting schedules.

#### Acceptance Criteria

1. THE Training_Plan_Service SHALL enforce that at most one Training_Plan per User has the state ACTIVE at any given time.
2. WHEN a User requests to activate a Training_Plan and the User already has a Training_Plan with state ACTIVE, THE Training_Plan_Service SHALL set the currently active plan's state to TERMINATED and update its `updatedAt` timestamp, before setting the requested plan's state to ACTIVE.
3. WHEN a User requests to activate a Training_Plan that has state NEW or COMPLETED, THE Training_Plan_Service SHALL set the plan's state to ACTIVE, update its `updatedAt` timestamp, and return HTTP 200 with the updated plan including all metadata fields (id, eventName, distance, duration, raceDate, targetPaceSecondsPerKm, aiModel, state, createdAt, updatedAt).
4. WHEN a User requests to activate a Training_Plan that already has state ACTIVE, THE Training_Plan_API SHALL return HTTP 400 with an error message indicating the plan is already active.
5. WHEN a User requests to activate a Training_Plan that has state TERMINATED, THE Training_Plan_API SHALL return HTTP 400 with an error message indicating a terminated plan cannot be reactivated.
6. THE Training_Plan_Service SHALL execute the state transition (terminate current active plan and activate new plan) within a single database transaction to prevent inconsistent states.
7. IF the database transaction for a state transition fails, THEN THE Training_Plan_Service SHALL roll back all changes so that neither plan's state is modified, and THE Training_Plan_API SHALL return HTTP 500 with an error message indicating the activation could not be completed.

### Requirement 3: Training Plan State Management

**User Story:** As a logged-in athlete, I want to manage the lifecycle state of my training plans, so that I can track which plans are current, finished, or abandoned.

#### Acceptance Criteria

1. WHEN a PUT request is sent to `/api/training-plans/{id}/activate` by an authenticated User who owns the Training_Plan, THE Training_Plan_API SHALL activate the plan following the rules defined in Requirement 2 and return HTTP 200 with the updated plan including all metadata fields (id, eventName, distance, duration, raceDate, targetPaceSecondsPerKm, aiModel, state, createdAt, updatedAt).
2. WHEN a PUT request is sent to `/api/training-plans/{id}/complete` by an authenticated User who owns the Training_Plan and the plan has state ACTIVE, THE Training_Plan_API SHALL set the plan's state to COMPLETED, update the `updatedAt` timestamp, and return HTTP 200 with the updated plan.
3. WHEN a PUT request is sent to `/api/training-plans/{id}/complete` by an authenticated User who owns the Training_Plan and the plan does not have state ACTIVE, THE Training_Plan_API SHALL return HTTP 400 with an error message indicating only active plans can be completed.
4. WHEN a PUT request is sent to `/api/training-plans/{id}/terminate` by an authenticated User who owns the Training_Plan and the plan has state ACTIVE or NEW, THE Training_Plan_API SHALL set the plan's state to TERMINATED, update the `updatedAt` timestamp, and return HTTP 200 with the updated plan.
5. WHEN a PUT request is sent to `/api/training-plans/{id}/terminate` by an authenticated User who owns the Training_Plan and the plan has state COMPLETED or TERMINATED, THE Training_Plan_API SHALL return HTTP 400 with an error message indicating the plan cannot be terminated from its current state.
6. WHEN a state transition request is sent to `/api/training-plans/{id}/activate`, `/api/training-plans/{id}/complete`, or `/api/training-plans/{id}/terminate` by an authenticated User who does not own the Training_Plan, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.
7. IF a state transition request is sent without a valid JWT token or with an expired token, THEN THE Training_Plan_API SHALL return HTTP 401 with an error message indicating authentication is required.
8. WHEN a state transition request is sent to `/api/training-plans/{id}/activate`, `/api/training-plans/{id}/complete`, or `/api/training-plans/{id}/terminate` with an identifier that does not exist or is not a valid UUID format, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.

### Requirement 4: Retrieve Training Plans

**User Story:** As a logged-in athlete, I want to view my training plans, so that I can see my active plan details and browse my plan history.

#### Acceptance Criteria

1. WHEN a GET request is sent to `/api/training-plans` by an authenticated User, THE Training_Plan_API SHALL return HTTP 200 with a JSON array of all Training Plans belonging to that User, each including metadata fields (id, eventName, distance, duration, raceDate, targetPaceSecondsPerKm, aiModel, trainingDays, longRunDay, state, createdAt, updatedAt) ordered by `createdAt` descending. IF the User has no Training Plans, THE Training_Plan_API SHALL return HTTP 200 with an empty JSON array.
2. WHEN a GET request is sent to `/api/training-plans/{id}` by an authenticated User who owns the Training_Plan, THE Training_Plan_API SHALL return HTTP 200 with the full Training Plan including all metadata fields (id, eventName, distance, duration, raceDate, targetPaceSecondsPerKm, aiModel, trainingDays, longRunDay, state, createdAt, updatedAt) and all associated Plan_Workouts each containing scheduling fields (weekNumber, dayOfWeek, orderInDay) and the referenced Workout's metadata (id, name, sportType, subSport, numValidSteps), grouped by week number and ordered by dayOfWeek ascending and then orderInDay ascending within each day.
3. WHEN a GET request is sent to `/api/training-plans/{id}` by an authenticated User who does not own the Training_Plan, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.
4. WHEN a GET request is sent to `/api/training-plans/{id}` with an identifier that does not exist or is not a valid UUID format, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.
5. WHEN a GET request is sent to `/api/training-plans/active` by an authenticated User who has an active Training_Plan, THE Training_Plan_API SHALL return HTTP 200 with the full active Training Plan in the same structure as criterion 2 (all metadata fields including trainingDays and longRunDay, all Plan_Workouts with scheduling fields and Workout metadata, grouped by week number and ordered by dayOfWeek ascending and orderInDay ascending).
6. WHEN a GET request is sent to `/api/training-plans/active` by an authenticated User who does not have an active Training_Plan, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating no active plan exists.
7. IF a GET request is sent to any `/api/training-plans` endpoint without a valid authentication token, THEN THE Training_Plan_API SHALL return HTTP 401.

### Requirement 5: Delete Training Plan

**User Story:** As a logged-in athlete, I want to delete a training plan I no longer need, so that my plan list stays clean and relevant.

#### Acceptance Criteria

1. WHEN a DELETE request is sent to `/api/training-plans/{id}` by an authenticated User who owns the Training_Plan and the plan has state NEW, COMPLETED, or TERMINATED, THE Training_Plan_API SHALL delete the Training_Plan and all associated Plan_Workout records and return HTTP 204 with no response body.
2. WHEN a DELETE request is sent to `/api/training-plans/{id}` by an authenticated User who owns the Training_Plan and the plan has state ACTIVE, THE Training_Plan_API SHALL return HTTP 400 with an error message indicating an active plan must be terminated before deletion.
3. WHEN a DELETE request is sent to `/api/training-plans/{id}` by an authenticated User who does not own the Training_Plan, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.
4. WHEN a DELETE request is sent to `/api/training-plans/{id}` with an identifier that does not exist or is not a valid UUID format, THE Training_Plan_API SHALL return HTTP 404 with an error message indicating the plan was not found.
5. IF a DELETE request is sent without a valid authentication token, THEN THE Training_Plan_API SHALL return HTTP 401.
6. THE Training_Plan_Service SHALL NOT delete the underlying Workout entities when a Training_Plan is deleted; only the Plan_Workout associations SHALL be removed.

### Requirement 6: Plan Workout Scheduling

**User Story:** As the AI plan generator, I want to assign workouts to specific days within a training plan's weekly structure, so that athletes have a clear day-by-day schedule.

#### Acceptance Criteria

1. THE Training_Plan_Service SHALL support assigning multiple Workouts to the same day within a Training Plan via the Plan_Workout entity, each with a distinct `orderInDay` value starting from 1 and incrementing sequentially (no gaps), up to a maximum of 5 Workouts per day.
2. THE Plan_Workout entity SHALL store `weekNumber` (integer, 1-based, representing the week within the plan), `dayOfWeek` (integer, 1=Monday through 7=Sunday), and `orderInDay` (integer, 1-based, representing the sequence when multiple workouts exist on the same day).
3. IF a Plan_Workout is submitted with a `weekNumber` that exceeds the plan's duration in weeks (8, 10, or 12 depending on Plan_Duration) or is less than 1, THEN THE Training_Plan_Service SHALL reject the assignment and return a validation error message indicating the week number is outside the valid range for the plan's duration.
4. IF a Plan_Workout is submitted with a `dayOfWeek` value less than 1 or greater than 7, THEN THE Training_Plan_Service SHALL reject the assignment and return a validation error message indicating the day of week is outside the valid range.
5. IF a Plan_Workout is submitted that would violate the unique constraint on (`training_plan_id`, `week_number`, `day_of_week`, `order_in_day`), THEN THE Training_Plan_Service SHALL reject the assignment and return an error message indicating a duplicate scheduling conflict exists for that day and position.
6. WHEN a Training_Plan is retrieved with its workouts, THE Training_Plan_API SHALL return Plan_Workouts grouped by `weekNumber`, sorted by `dayOfWeek` ascending and then `orderInDay` ascending within each day.
7. THE Training_Plan_Service SHALL only allow workout assignment to a Training_Plan that has state NEW; attempts to assign workouts to a plan with state ACTIVE, COMPLETED, or TERMINATED SHALL be rejected with an error message indicating the plan's state does not permit scheduling modifications.
8. IF a Plan_Workout references a `workout_id` that does not correspond to an existing Workout entity, THEN THE Training_Plan_Service SHALL reject the assignment and return an error message indicating the referenced workout was not found.

### Requirement 7: Training Plan Data Persistence

**User Story:** As a developer, I want training plans and their workout associations to be persisted in PostgreSQL with proper schema and constraints, so that data integrity is maintained.

#### Acceptance Criteria

1. THE Training_Plan_Service SHALL persist Training Plans in the `trainer.training_plans` table with columns: `id` (UUID, primary key, DEFAULT gen_random_uuid()), `user_id` (BIGINT, foreign key to `trainer.users.id`, NOT NULL), `event_name` (VARCHAR 100, NOT NULL), `distance` (VARCHAR 20, NOT NULL), `duration` (VARCHAR 10, NOT NULL), `race_date` (DATE, NOT NULL), `target_pace_seconds_per_km` (INTEGER, NOT NULL), `ai_model` (VARCHAR 20, NOT NULL), `training_days` (INTEGER ARRAY, NOT NULL), `long_run_day` (INTEGER, NOT NULL, CHECK BETWEEN 1 AND 7), `state` (VARCHAR 20, NOT NULL, DEFAULT 'NEW'), `created_at` (TIMESTAMPTZ, NOT NULL, DEFAULT NOW()), `updated_at` (TIMESTAMPTZ, NOT NULL, DEFAULT NOW()).
2. THE Training_Plan_Service SHALL persist Plan_Workouts in the `trainer.plan_workouts` table with columns: `id` (UUID, primary key, DEFAULT gen_random_uuid()), `training_plan_id` (UUID, foreign key to `trainer.training_plans.id` ON DELETE CASCADE, NOT NULL), `workout_id` (UUID, foreign key to `trainer.workouts.id` ON DELETE RESTRICT, NOT NULL), `week_number` (INTEGER, NOT NULL, CHECK > 0), `day_of_week` (INTEGER, NOT NULL, CHECK BETWEEN 1 AND 7), `order_in_day` (INTEGER, NOT NULL, CHECK > 0), with a UNIQUE constraint on (`training_plan_id`, `week_number`, `day_of_week`, `order_in_day`).
3. THE Training_Plan_Service SHALL enforce a cascading delete on Plan_Workouts: when a Training_Plan is deleted, all associated Plan_Workout records SHALL be deleted automatically via ON DELETE CASCADE on the `training_plan_id` foreign key.
4. THE Training_Plan_Service SHALL prevent deletion of a Workout that is referenced by any Plan_Workout record via ON DELETE RESTRICT on the `workout_id` foreign key, leaving referenced Workouts intact when a Training_Plan is deleted.
5. THE Flyway migration SHALL create an index on `trainer.training_plans.user_id` to optimise queries filtering plans by user.
6. THE Flyway migration SHALL create an index on `trainer.training_plans.state` to optimise queries filtering plans by state.
7. THE Flyway migration SHALL create an index on `trainer.plan_workouts.training_plan_id` to optimise queries loading workouts for a plan.
8. THE Training_Plan_Service SHALL use UUID as the identifier type for both Training_Plan and Plan_Workout entities.
9. THE Training_Plan_Service SHALL create the database schema using a Flyway migration script named `V4__training_plan_schema.sql` placed in `src/main/resources/db/migration/`, following the project's `V{n}__{description}.sql` naming convention where `n` is the next available version number.

### Requirement 8: Active Plan View UI

**User Story:** As a logged-in athlete, I want to see my active training plan displayed as weekly cards with expandable workout details, so that I can easily follow my training schedule week by week.

#### Acceptance Criteria

1. THE Active_Plan_View SHALL display the active Training Plan's metadata (event name, distance, duration, race date formatted as DD/MM/YYYY, target pace converted from seconds per kilometre and displayed as MM:SS/km, training days displayed as comma-separated day names e.g. "Mon, Wed, Fri, Sun", long run day displayed as a day name e.g. "Long Run: Saturday") at the top of the view in a summary header section.
2. THE Active_Plan_View SHALL render one Week_Card per week in the plan, arranged vertically in chronological order (week 1 at the top, week N at the bottom).
3. EACH Week_Card SHALL display a summary including the week number (e.g., "Week 1"), the total number of workouts scheduled for that week, and a comma-separated list of distinct workout types scheduled for that week (e.g., "Easy Run, Intervals, Long Run").
4. WHEN the athlete clicks on a collapsed Week_Card, THE Active_Plan_View SHALL expand the card to reveal individual workout cards for each scheduled workout in that week, ordered by dayOfWeek ascending and then orderInDay ascending within each day.
5. EACH expanded workout card SHALL display the workout name, the scheduled day name (e.g., "Monday"), and a summary of the workout structure (total duration or distance, intensity level).
6. WHEN the athlete clicks on an already-expanded Week_Card, THE Active_Plan_View SHALL collapse the card back to its summary state, hiding the individual workout cards.
7. WHEN no active Training Plan exists, THE Active_Plan_View SHALL display a message "No active training plan" and a "Create Plan" button that opens the plan creation form.
8. WHILE the Active_Plan_View is loading plan data from the Training_Plan_API, THE Active_Plan_View SHALL display a PrimeNG loading spinner centred in the view.
9. WHEN the Training_Plan_API returns an error, THE Active_Plan_View SHALL display a PrimeNG toast error notification with the error message returned by the API.
10. THE Active_Plan_View SHALL only have one Week_Card expanded at a time; expanding a new Week_Card SHALL automatically collapse the previously expanded card.

### Requirement 9: Plan List View UI

**User Story:** As a logged-in athlete, I want to see all my non-active training plans in a list with management actions, so that I can organise, activate, or remove old plans.

#### Acceptance Criteria

1. THE Plan_List_View SHALL display all Training Plans belonging to the authenticated User that do not have state ACTIVE, listed with their event name, distance, duration, race date, and current state.
2. THE Plan_List_View SHALL order plans by `createdAt` descending (most recent first).
3. THE Plan_List_View SHALL display a visual state indicator (badge or tag) for each plan showing its current state (NEW, COMPLETED, TERMINATED) using a distinct colour for each state so that no two states share the same colour.
4. EACH plan entry in the Plan_List_View SHALL provide an "Activate" action button. THE "Activate" button SHALL be enabled for plans with state NEW or COMPLETED and disabled for plans with state TERMINATED.
5. EACH plan entry in the Plan_List_View SHALL provide a "Delete" action button. THE "Delete" button SHALL be enabled for plans with state NEW, COMPLETED, or TERMINATED.
6. WHEN the athlete clicks "Activate" on a plan, THE Plan_List_View SHALL display a confirmation dialog warning that the current active plan (if any) will be terminated, and proceed with activation only upon confirmation. IF the athlete cancels the confirmation dialog, THEN THE Plan_List_View SHALL close the dialog and take no further action.
7. WHEN activation succeeds, THE Plan_List_View SHALL remove the newly activated plan from the list, display a success notification, and if a previously active plan was terminated, add that plan to the list with state TERMINATED.
8. WHEN the athlete clicks "Delete" on a plan, THE Plan_List_View SHALL display a confirmation dialog and proceed with deletion only upon confirmation. IF the athlete cancels the confirmation dialog, THEN THE Plan_List_View SHALL close the dialog and take no further action.
9. WHEN deletion succeeds, THE Plan_List_View SHALL remove the plan from the list and display a success notification.
10. WHEN the list is empty, THE Plan_List_View SHALL display a message indicating no plans exist and a button to navigate to plan creation.
11. WHILE a management action (activate or delete) is in progress, THE Plan_List_View SHALL disable the corresponding action button and display a loading indicator on that button.
12. IF the Training_Plan_API returns an error during an activate or delete action, THEN THE Plan_List_View SHALL re-enable the action button, remove the loading indicator, and display an error notification with the error message returned by the API.
13. WHILE the Plan_List_View is loading plan data from the Training_Plan_API, THE Plan_List_View SHALL display a loading indicator.

### Requirement 10: Plans Page Navigation and Tabs

**User Story:** As a logged-in athlete, I want the training plans feature to be accessible via navigation with two clear tabs, so that I can quickly switch between viewing my active plan and managing all plans.

#### Acceptance Criteria

1. THE Plans_Page SHALL be accessible via the application's main navigation menu under a "Training Plans" entry that is rendered as an enabled, clickable menu item navigating to the `/plans` route.
2. THE Plans_Page SHALL contain two tabs labelled "Active Plan" and "My Plans", displayed in that order from left to right.
3. WHEN the Plans_Page loads, THE Plans_Page SHALL default to the "Active Plan" tab as the selected and visible tab.
4. WHEN the athlete switches between tabs, THE Plans_Page SHALL display the corresponding view (Active_Plan_View or Plan_List_View) without a full page reload.
5. THE Plans_Page SHALL use PrimeNG TabView component for tab navigation.
6. THE Plans_Page SHALL be implemented as a lazy-loaded Angular standalone component accessible via the route `/plans`.
7. IF an unauthenticated user attempts to access the `/plans` route, THEN THE application SHALL redirect the user to the login page.

### Requirement 11: Plan Creation Form UI

**User Story:** As a logged-in athlete, I want a form to input my race details and preferences for plan creation, so that I can request an AI-generated training plan tailored to my goals.

#### Acceptance Criteria

1. THE Plans_Page SHALL provide a "Create Plan" button accessible from both tabs that opens a plan creation form as a PrimeNG dialog.
2. THE plan creation form SHALL display input fields for: `eventName` (text input, required, max 100 characters), `distance` (dropdown with options: 5K, 10K, Half-Marathon, Marathon), `duration` (dropdown with options: 8 Weeks, 10 Weeks, 12 Weeks), `raceDate` (date picker restricted to future dates, where future means any date after today based on the client's local date), `targetPaceSecondsPerKm` (pace input displayed and accepted in MM:SS/km format, required, range 2:30–15:00/km; the UI SHALL convert the entered MM:SS/km value to seconds per kilometre before sending to the Training_Plan_API for storage), `aiModel` (dropdown with options: ChatGPT, Claude, Gemini, Kiro, Dummy), `trainingDays` (multi-select input for days of the week: Monday, Tuesday, Wednesday, Thursday, Friday, Saturday, Sunday; required, at least 1 day must be selected), and `longRunDay` (dropdown that only displays the days currently selected in `trainingDays`; required, disabled until at least one training day is selected).
3. WHEN the athlete submits the form with valid data, THE plan creation form SHALL send a POST request to the Training_Plan_API and display a success notification indicating the plan was created upon receiving HTTP 201.
4. WHEN the athlete submits the form with invalid data, THE plan creation form SHALL display inline validation errors for each invalid field without sending a request to the Training_Plan_API. Validation rules are: `eventName` is required and must not exceed 100 characters; `distance`, `duration`, and `aiModel` are required selections; `raceDate` is required and must be a date after today; `targetPaceSecondsPerKm` is required and must be between 150 and 900 seconds inclusive (2:30–15:00/km); `trainingDays` is required and must contain at least 1 day with values between 1 and 7 and no duplicates; `longRunDay` is required and must be one of the selected `trainingDays` values.
5. WHILE the creation request is in progress, THE plan creation form SHALL disable the submit button and display a loading indicator.
6. WHEN the Training_Plan_API returns an error response, THE plan creation form SHALL display an error notification containing the error message from the response body.
7. WHEN plan creation succeeds, THE plan creation form SHALL close, THE Plans_Page SHALL switch to the "My Plans" tab, and the newly created plan SHALL appear in the Plan_List_View with state NEW.
8. THE plan creation form SHALL provide a "Cancel" button that closes the dialog without submitting data or modifying any plan state.
